# 项目主线：让同一个小游戏随学习成长

日期：2026-09-15。状态：课程衔接设计，不是已完成的新游戏版本。

本文件补充[课程索引](lesson-index.md)和[学习深度合同](learning-contract.md)。本轮不扩写Godot、Blender或网页实现，不调用OpenMAIC生成。已有配套和新课件的实际状态仍分别记录于[交付进度](delivery-status.md)。

## 1. 一个主项目，不等于所有实验都塞进主场景

主项目暂称「星光小庭院」：单机、一个小场地、一条清楚的收集路线、少量平台、10颗星星；角色能走跑跳，镜头可用，收集可感知、可完成、可重开。风格方向为温暖、童趣、风格化，具体色彩和比例由风格卡及实际观察决定。名称和题材是教学建议，不涉及改名现有工程。

初级不增加战斗、背包、任务树、开放世界、联网或复杂角色绑定。中级可在同一个庭院中选择一个小扩展，不因为学了新术语就添加系统。

采用两层结构：

- **可重置的概念实验**：只保留理解本课所需的对象和控件。材质可用两个球，门轴可用一块板；错误在可恢复副本里制造。
- **持续成长的游戏项目**：把已经理解和验收的设置、资产或功能接入庭院，再确认原有功能仍正常。

连接顺序是「观察示范 → 先预测 → 小实验验证 → AI辅助制作初稿 → 人选择并微调 → 接入庭院 → 旧功能回归 → 换情境复测」。不要求一次做完，认识类K内容也不强制实操。

不是先学完所有理论再做项目，也不是一开始让AI生成整个游戏。已有完整参考工程只用来展示目标或排错，不要求新手读完全部源码。

## 2. 内容制作顺序和学员学习顺序是两回事

**当前制作顺序：** 先完善课件、AI协作卡和图示设计，再生成并检查代表课堂，最后补齐真实工程的逐课起始状态、参考结果和素材。这不意味着将来学员必须先读完全部课件才能操作软件。

**将来的学习顺序：** 一个小知识点后就做一次相应体验，掌握后迁入主项目。每课最多推进一项可观察的变化；可以是功能、美术、手感、可靠性或证据，不必新增玩法。

## 3. 项目里程碑

下表是目标与验收设计；P00–P07是里程碑，不是新的知识难度或课程系列。当前已发布课号保留，方便与现有45课对应。未来ABCDE主题编号迁移要有旧新映射，不能把旧B08误读成新版同号课。

|里程碑|主项目得到什么|AI承担的准备|学员亲自判断/微调|晋级前看什么|
|---|---|---|---|---|
|P00 定目标|一页风格卡、一个小玩法目标、目标设备记录|分析已提供参考、把抽象词改成几项可验证选择|选形状、比例、主次和观察距离；舍弃无关效果|能说出喜欢哪项、不要哪项，不按艺术家名字盲选|
|P01 小场地|地面、墙、平台和可观察的灰盒布局|准备最小场景或指导放入实例|选对节点，调整位置/尺度，核对影响范围|移动整体不会只把外观挪走；可恢复到基线|
|P02 可探索|阻挡、走跑跳和第三人称镜头|实现输入与控制样板，暴露少数手感参数|试速度、起跳、镜头距离/FOV/灵敏度，走同一路线对照|墙仍挡人、空中不能无限跳、镜头不过度遮挡；不以会背API过关|
|P03 可收集|一份可用星星资产、导入与一次性拾取|协助制作/改造静态资产，写检测和事件初稿|检查尺寸/原点/材质共享，选择触发范围，回放事件顺序|正确对象只计一次；重导入不破坏玩法包装|
|P04 完整小循环|计数、完成、重开与清楚的成功反馈|搭好UI与简单反馈初稿|检查静音可读性、提示强度和最后一颗星的体验|从启动到收齐再重开能走通，不只看星星消失|
|P05 初级成品|同一庭院的基础风格、可读光照和测量记录|提供局部美化候选、协助测试与回归|固定机位调光/材质；在真实游戏距离看效果；做一个单变量性能对照|美化后路径和星星仍清楚，拾取/镜头/重开未退化；换拾取物后仍理解|
|P06 中级小升级|现成角色动画；一个机关或简单敌人；必要的恢复/设置与导出|复用现成资源和组件，准备兼容与恢复检查|选择资源、检查切换/脚滑/机关与角色关系、测试陌生机器或干净数据启动|只验所选路线；不强迫同时做敌人、机关、背包和复杂任务|
|P07 美术精修/专项|统一的小资产套件，或修复一个真实技术问题|基于稳定基底制作少量变体；辅助专项目标|按大形→结构→表面修整，决定收益是否值得，检查风格与功能回归|不是把所有高级特性启用；不用的专项可以只留在实验中|

P00的风格目标不是一成不变的答案。后续发现目标不合适可以修订风格卡，但先用一件样本验证，不批量重做全库。

## 4. 现有课程怎样回到这个项目

|现有课件|游戏里的落点|不扩大范围的边界|
|---|---|---|
|R01|庭院风格卡与参考描述|先能说具体，不做大型世界观|
|B01A、B02|地面/墙/平台的尺寸位置与实例|灰盒即可，不需要完整角色|
|B04、B03、B05|墙的阻挡、移动与跳台体验|先给参考控制器，不要求从零写物理|
|B01B、B06|镜头的父子关系和旋转中心|复杂旋转数学不进入初级|
|R02、B07|星星和简单道具的剪影、比例与质量检查|允许使用可编辑基底；不是手工建模速度考核|
|R03、B08|星星与背景的明暗关系、材质参数和共享范围|先固定环境，不做复杂贴图|
|B09、B10|资产更新后仍能拾取，事件只计一次|不把一次拾取扩成背包架构|
|B11、B12|反馈、计数、完成和重开|少量可靠反馈，不追求特效数量|
|B13、R04|路径/目标的光照可读性；从参考提取一个视觉原则|作品研究的产物也可以是一张对照分析卡|
|B14、B15、B16|可复现测量、AI改动回归、新拾取物迁移|不靠关闭需求假装修好或优化|
|I01、I02、I03|换现成角色，动作状态可靠，资源影响范围清楚|不从零绑定，不实现通用动画框架|
|I04、I09|庭院的一扇门或一个可交互对象|先选一个机制；无需新关卡|
|I05、I06、I07|模块拼接、简单UV、统一光感、一次性能决策|有证据才采用复杂优化|
|I08|可选：庭院内一个简单巡逻对象|纯机关路线不学也能结业|
|I10、I11、I12|保存必要进度/设置，检查恢复和最终交付|选定一个平台；不做云同步|
|R05、R06、R07、R08|同一庭院换成一套统一的自有变体资产|资产少而可靠；不以数量判成品质量|
|X01、X02|可选：一个动作资源接入及节奏试验|不为练武打把收集游戏强改成战斗游戏|
|A01、A02、A03、A04、A06|按实际问题选择一个优化/效果/旋转/场景实验|每个专项都可在隔离实验中完成；证明有益才接回庭院|
|A05|多人需求的认识与取舍记录|全K选修；不把单机项目改成联网项目|

主题分类与学习路径分开：ABCDE可作为基础、Godot、美术、AI协作和进阶等主题入口，但AI协作应从第一课就穿插；不要先读完整个A，再等到D才开始用AI。主题新编号尚未在本次修改中批量迁移。

## 5. 每课必须回答的「主项目增量卡」

补充[OpenMAIC项目衔接模板](../openmaic/project-integration-template.md)，下一轮逐课回填作者源时一并展开到学生稿和教师稿，不只编辑生成产物。

```text
本课产出：本次只让游戏/资产/判断多一项什么能力？
开始状态：已有且经过哪一层验证的功能是什么？
预期证据：同机位前后图、运行片段、状态记录或可核对的设置；示意必须标注。
AI准备：允许改什么？不准改什么？没有工具连接时交什么脚本或操作单？
我的预测：预计变化及一个理由。
我的微调：最多两三项有价值参数；每项先保留原值，一次改变一项。
接入位置：哪份资产、哪个节点职责或哪个状态；无需背完整路径。
回归：之前至少一项最相关的功能仍然正常。
本课停止线：现在不做什么；K只理解不深挖。
学习证据：我改了什么、看见什么、为什么；是否用了根因提示。
复测：换对象/数值/限制后的一个小问题。
```

不是每课都要造新素材或写报告。风格选择可以贡献风格卡，性能课可以贡献一次测量和“不优化”的决定。K认识课可以贡献一条用途/风险说明。

## 6. 例子：学光照，不是重新生成一个场景

在已完成P04的庭院里，目标是“傍晚但星星和路径仍看得清”。小实验先区分主光、环境和发光；然后在同一庭院做局部光照初稿。

给AI当前截图、实际软件版本、渲染器和一张使用条件允许的参考图。点明只借鉴色温和明暗关系，不复刻参考图的全部构图或角色。AI先提出少量候选、记录基线，列明将改哪些节点/参数；不重写玩家、计数和关卡。

学员固定游戏机位，先调主光能量，再恢复/对照；之后才改方向或环境强度。不是同时改曝光、材质、自发光和灯光后猜原因。三次随机重生成仍说不清差异时，回到一个可观察变量，不继续堆提示词。

最后在游戏视角走一圈：能发现星星吗？暗角会误判为死路吗？拾取、计数和重开还正常吗？保留改前/改后两张同机位图和相关参数即可，不要求长篇美术分析。

这是预期实验而非保证某个API给出某张图。光能量和相机FOV等入口以[Light3D文档](https://docs.godotengine.org/en/stable/classes/class_light3d.html)与[Camera3D文档](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)为依据；具体视觉效果仍需在所选渲染器中实测。

## 7. 何时AI，何时自己动手

结构搭建、样板代码、成批重命名或同规则变体：优先让AI准备，学员检查范围和结果。单一、连续且即时可见的差异：先试拖动/键盘输入数值，再决定是否需要AI。复合效果或原因未知：让AI提出可证伪假设，先做最小对照，不反复改全局。

模型/插件造成的版本错误、执行遗漏等属于需要按当前工具重新观察的风险，未来是否改善要靠复测，不保证改善时间。目标、可接受结果、资源条件、性能预算和取舍仍由项目负责人批准；这是责任划分，不是宣称AI永远不能参与审美或自动微调。

## 8. 连续成长也要允许失败和回退

每个里程碑保留一个已验收快照；后续配套可通过打包的起始/参考状态或Git标签提供，不为每节课建长期分支。本文件没有创建这些标签或配套。学员坏了可恢复，也可用参考状态继续下一课，不需要因一个错误重做全部课程。

测试只覆盖已经实现的功能。先看当前课堂的一个增量，再看一项受影响旧能力；不要每节课重复整张结业卷。阶段结业才从头走完整循环。

工程通过与学习通过分别记录：现成代码可通过功能测试，但学员如果不能选择修改对象、解释观察结果，就仍需一个变式练习；不要求为证明学习而闭卷重写代码。

## 9. 为什么这样设计，不直接称为「最佳」

IES/WWC的教学指南建议把示例与自主解决问题交替、把抽象与具体表现连接、结合图示与语言，并用测验和间隔复习再次接触关键内容。这支持本设计采用的若干教学环节，不证明「同一个Godot项目+AI」对所有学员都最优。

来源：[Organizing Instruction and Study to Improve Student Learning](https://ies.ed.gov/ncee/wwc/PracticeGuide/1)（2007，2026-09-15核对网页）。本课程的实际负担与效果还要通过无根因提示的变式任务和隔次复测检查，不能用作品漂亮、AI写了多少代码或按钮点了多少次代替。
